# Timezone Converter

A small, single-page web app for converting a date and time from one timezone to another. Built with vanilla JavaScript and Tailwind CSS, with no frontend framework and no build step for the JS.

**Live demo:** _add your deployed link here_

## Features

- Pick a **date**, a **24-hour time** and a **source timezone**, then choose a **target timezone**. The result updates instantly.
- Every IANA timezone is available, sorted by UTC offset, with the offset shown in each option (for example `Asia/Kolkata (UTC+05:30)`).
- Defaults to your browser's timezone and the current date and time.
- **Save conversions** to a list below the form. Saved entries persist in your browser's `localStorage` and can be deleted individually.
- **Light, dark and system themes**. The system option follows your OS setting live, and your choice is remembered. An inline script applies the theme before first paint, so there is no flash of the wrong theme.
- DST-aware: conversions use the actual selected date, so daylight saving changes are handled correctly.

## Tech stack

| Purpose | Tool |
|---|---|
| Language | Vanilla JavaScript (ES modules not required) |
| Timezone maths | [Luxon](https://moment.github.io/luxon/) 3, loaded from a CDN |
| Styling | [Tailwind CSS](https://tailwindcss.com/) v4 via the standalone CLI |
| Storage | Browser `localStorage` |
| Hosting | Any static host (GitHub Pages, Netlify, Cloudflare Pages, etc.) |

## Getting started

Prerequisites: [Node.js](https://nodejs.org/) (only needed for the Tailwind CLI).

```bash
# install dependencies
npm install

# terminal 1: rebuild CSS on every change
npm run dev

# terminal 2: serve the site locally
npx serve .
# or: python3 -m http.server
```

Then open the local address the server prints (for example `http://localhost:3000`).

### Production build

```bash
npm run build
```

This writes a minified `dist/output.css`. Commit it, because static hosts serve the committed files directly.

## Deployment

The site is fully static, so any static host works.

**GitHub Pages:** Settings → Pages → Deploy from a branch → `main` / `(root)`.

Project sites are served from a sub-path (`/<repo-name>/`), so all asset paths in `index.html` are relative (`./dist/output.css`, `./src/main.js`). Keep them that way.

**Netlify / Cloudflare Pages:** connect the repo, leave the build command empty, and set the publish directory to the repo root.

## How it works

- **Timezone list:** `Intl.supportedValuesOf("timeZone")` supplies the zone names. Each is sorted by its current UTC offset using Luxon.
- **Conversion:** `DateTime.fromISO(..., { zone })` reads the inputs as wall-clock time in the source zone, and `.setZone()` re-expresses the same instant in the target zone.
- **Saved entries** store the original inputs (date, hour, minute, source zone, target zone), not the computed result. The result is recomputed when rendering. Data lives under the key `tz-converter:saved`.
- **Theming:** colours are defined as named tokens (`page`, `card`, `ink`, `muted`, `line`, `accent`) in `src/input.css`. The `.dark` class on `<html>` swaps their values, so components never need `dark:` variants. The preference is stored under `tz-converter:theme`.

## Known limitations

- The offsets shown in the dropdown labels and the sort order reflect **today's** offsets. The converted result itself always uses the selected date.
- Saved conversions are stored per browser and per device. They do not sync.
- Luxon is loaded from a CDN, so the first visit needs a network connection.

## Future plans

- [ ] **Swap button:** flip the "from" and "to" timezones with one click.
- [ ] **Clear all button:** remove every saved conversion at once (ideally with a confirmation).
- [ ] **Future-date events and reminders:** when a conversion lands on a future date, offer to save it as a note, to-do or event item and send a reminder before it happens. This is a much bigger change than the items above, and it raises a few design questions:
  - A purely static site cannot push notifications while the browser is closed. Possible approaches include an exported `.ics` calendar file (the simplest option, and it lets the user's calendar app handle the reminder), the Notification API with a service worker (limited reliability when the app is not open), or a small backend with web push or email (the most reliable, but it means leaving pure static hosting).
  - Events would need a richer data model than the current saved-conversion entries, such as a title, a notes field, and a reminder offset.
